# personal-dev 开发约束与精简 Skill 设计

## 授权与范围

用户已确认讨论结果，并显式调用 `dev-delegate`，指定子代理 6 Luna，授权主模型整理 spec / plan 后直接开始实现、独立验收、主模型亲自验证 Codex / Claude Code 兼容性，最后提交并推送当前主检出分支。无需再次等待计划批准。

在 `plugins/personal-dev/skills/` 新增自有 `dev-yagni` 与 `dev-simplify`。两个 Skill 各用简短 `SKILL.md` 和 `agents/openai.yaml`，不新增脚本、依赖、报告模板、后台服务或自动流程。更新直接相关的包装、说明和现有测试。保留原有 `dev-delegate` / `dev-review` 行为；不修改第三方快照、sources、lock、全局配置或其他客户端。

## 已确认行为

| 条件 | dev-yagni | dev-simplify |
| --- | --- | --- |
| 未显式调用 | 不执行 | 不执行 |
| 默认调用 | 对当前明确开发任务应用约束并执行 | 只读给出精简建议，等待确认 |
| 明确先看方案 / 先讨论 | 只读提出方案，等待确认 | 只读提出建议，等待确认 |
| 明确执行 / 直接做 | 直接执行当前授权任务 | 直接精简授权范围并验证 |
| 后续确认 | 按已确认方案继续同一任务 | 按已确认建议继续同一范围 |
| 默认执行者 | 当前模型 | 当前模型 |

判断完整语义及否定、引用和讨论语境，不做关键词匹配。引用调用名或粘贴讨论内容不构成执行请求；“暂时不要执行”优先于默认行为。只有调用名且缺少明确目标时询问一次关键目标，不能自行发明需求。

## 调用与生命周期

- Codex 完整入口为 `$personal-dev:dev-yagni` / `$personal-dev:dev-simplify`；Claude 为 `/personal-dev:dev-yagni` / `/personal-dev:dev-simplify`。不新增别名机制，裸名称行为按真实客户端证据说明。
- Claude frontmatter `disable-model-invocation: true`；Codex metadata `policy.allow_implicit_invocation: false`；描述及正文同时限定用户显式调用。
- 两者不互相调用、不自动串联，也不自动调用 `dev-delegate` / `dev-review`。用户显式选择 `dev-delegate` 时，主模型把当前任务已启用的约束、已确认方案、允许范围和验证条件交给编码及独立验收代理，不默认派代理，不重复实现委派策略。
- 用户同时或先后明确调用委派都属于显式选择；“先给方案 / 建议”的限制仍需保留，不能以委派绕过确认。双端原生命令语法按实际加载验证，不假设两条命令在同一消息中都会直接注入正文。
- 未调用时不主动加载正文；Codex 目录元数据可能可见。调用后已进入对话的正文由 Harness 管理，不能保证自动卸载；指令只作用于当前任务，任务结束或明确更换任务后不继续生效。

## dev-yagni 职责

面向开发前及开发中。读取当前目标项目规则、需求和直接相关实现，采用最小但完整的方案：只实现当前明确需求，不增加未来假设、无真实用途的抽象、配置、扩展点或功能。遵循项目既有模式，保留已经确认的需求、接口与架构，不借反过度设计撤销已完成内容或清理无关代码。

按真实适用性优先复用项目已有能力与依赖，再考虑标准库或成熟第三方依赖。新依赖按目标项目规则说明必要性、替代方案与维护代价；不得仅因调用此 Skill 就安装或升级依赖，按当前任务已有授权和项目规则处理。必要的校验、错误处理、安全、权限、事务、并发、资源释放与可排查性不能被“少写代码”削弱。

方案模式用聊天输出目标、最小方案及有实质影响的取舍；执行模式完成授权任务并按风险验证。无需强制长计划、报告文件或全量测试。

## dev-simplify 职责

功能完成后的行为等价精简。默认范围是当前目标项目工作区的暂存、未暂存及新增源码；有明确文件、目录、commit、分支差异等范围时遵从。Git 不可用或无 diff 且用户未指定范围时先询问，不自动扩大到全项目。保留用户已有改动；混杂且无法可靠归属时澄清一次。可以读取必要的直接调用点，不能据此扩大编辑范围。

候选项包括无实际价值的中间层、无意义抽象、明显冗余分支和可安全减少的重复逻辑。衡量可读性、职责和维护成本，不以行数、去重率或代码技巧作为指标，允许“无需精简”。

保持行为、接口、数据契约、错误处理、安全、权限、事务、调用顺序、外部请求、并发、必要日志及资源生命周期；不引入性能回退。发现实际 Bug 单独报告，修 Bug 需要明确授权，不能混进精简。不确定行为等价或验证条件不足的候选项保留为建议，不能宣称已验证；已授权编辑后做相关有效检查与 diff 核对，不强制全量流程。

建议模式在聊天中简述范围、候选改动、收益和验证方式，等待确认；执行模式进行可确认安全的精简并报告实际改动、验证及未验证项。

## 项目与权限边界

Skill 维护在 agent-marketplace，执行目标是调用时当前工作目录对应的项目，不写死维护仓库路径，不跨项目，不改全局配置。遵守目标项目 AGENTS / 版本 / 风格 / 验证要求，调用不额外授予安装、升级、提交、推送、发布或外部写入权限。Git 收尾遵守目标项目授权与规则。

## 验收

1. 包装与目录：四个 personal-dev Skill 均可发现，两个新入口具有双端手动策略，无脚本与隐藏加载链，manifest 与 catalog 一致，第三方来源不变。
2. 行为场景：普通请求 / 引用不触发；YAGNI 默认执行与先方案；simplify 默认建议、明确执行、后续确认；缺少目标 / 空 diff / 混杂改动 / 无安全候选；用户显式委派保持确认边界及交接约束。
3. 复用 unittest，先观察新包装契约失败，再实现通过；以独立代理检验实际指令理解，不把字符串断言当作模型行为测试。
4. 主模型亲自使用隔离 fixture 在当前真实 Codex / Claude CLI 上验证安装、发现、普通请求不注入正文、显式调用注入及必要的组合入口；模型推理由 localhost 捕获后拒绝，不改日常配置。记录组合语法的真实边界。
5. 主模型核对最终 diff 与相关回归，`git diff --check`，只提交任务文件，回到原主检出交付、非强制推送。隔离加载和场景验证不能表述为任意生产项目或桌面 UI 全流程已验证。
