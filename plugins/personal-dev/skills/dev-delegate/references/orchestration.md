# 任务编排与进度恢复

本文件是 [dev-delegate](../SKILL.md) 在多任务、复杂 / 高风险任务或确需进度恢复时的派发前必读契约，由主模型执行；单个简单任务使用主 Skill 的精简交接，角色交接见 [roles.md](roles.md)。只使用文本记录和当前 Harness 原生工具，不要求调度脚本、数据库、任务图或独立工作树。

## 计划冲突预检

首次派发前，以用户已确认的需求、规格和项目规则为依据检查当前任务安排；没有单独计划文件时直接检查已确认的任务要求，不为预检新建设计文档。

- 核对任务与需求中的关键值、接口签名、字段含义及验收条件，检查实现安排和验证要求是否互相矛盾。
- 对共享文件、接口或上下游产出的任务，逐组核对“谁提供什么、谁使用什么”、依赖顺序与写入范围；发现计划缺陷由主模型修正安排，业务目标或授权边界的变化交用户决定。
- 有 ledger 时简短记录检查对象、依据、冲突与处理结论；无 ledger 时把必要结论写入派发交接，不增加报告。未解决的关键契约不能派发。编码与验收使用同一版任务要求和精确约束，需求修订后同步受影响任务。

## 任务与依赖

多任务或确需进度恢复时，每项至少明确 `task_id`、`goal`、`depends_on`、`write_scope`、`can_parallel`。ID 在本次执行内唯一且稳定；单任务写在交接消息即可，多任务写入 ledger。按可独立验收的完整功能或修复点拆分，同一功能的技术层优先由一个编码代理完成后统一验收；确需拆开时再记录任务间依赖。

- `depends_on` 使用任务 ID，检查直接和间接依赖。接口、数据结构、调用链或前项产出是后项输入时必须记录，不能因文件不同而省略。
- `write_scope` 列出相对目标项目的具体文件或目录，包含实现、测试、配置、生成文件和验证命令的写入。目录包含关系也算重叠；边界不清先串行，派发前补齐。
- `can_parallel` 只是候选资格，不是立即启动许可。主模型逐对检查依赖、范围和共享契约，记录允许或禁止并行的原因。
- 上游 ledger `DONE`、独立验收通过且相关契约已确定，才解除依赖。Coder 的 `DONE` 报告只进入 `REVIEW`。上游返工使已验收的契约改变时，暂停下游，复核受影响证据，不重开上游预算。
- 缺失依赖 ID、自依赖或循环先由主模型修正拆分；无法判断时报告阻塞，不忽略依赖抢跑。简单单任务不生成任务图。

## 有限并行

默认 `max_coders: 1`。只有本批所有任务逐对满足以下条件，才设置为 `2`；确有第三个安全独立任务且槽位足够时可设 `3`，编码硬上限为三个。用户指定更低上限时遵从，不因“尽快”放宽条件。

1. 没有直接或间接依赖，所需上游已经通过验收。
2. 修改范围明确且 `write_scope` 不重叠。
3. 不共享正在变化的接口、schema、公共配置或核心契约。
4. 当前原生工具和工作区确实支持并发子代理，主模型判断合并风险低。
5. 验证所用的输出目录、端口、fixture 或其他有副作用资源不冲突；不能隔离时将这些验证串行安排，不能确认时整项串行。

拆成不同任务的 DTO / Service / Controller / 前端调用等上下游任务、可能编辑同一文件、目录范围包含、共同修改接口或等待契约确定，均串行。不得让多个写代理在同一工作区同时修改可能重叠的文件；不为并行自动创建 worktree、多分支 merge 或 Agent Teams。

每次启动和修复前重新检查上述条件。编码数包含初次实现、返工和仍在运行的后台写任务；通知未到、取消未确认不能视为已释放。总活动代理数还需计入 Reviewer 和 Harness 其他代理。槽位不足先等待或减小本批，不突破三个编码上限。

任一任务第二轮复验仍有真实阻塞项时停止全流程：停止新派发，用当前原生能力中断尚在运行的工作并核实状态，保存已完成成果与未确认项；不能任由其他任务继续写入后宣称已经停止。无法中断时报告仍活动的代理，不释放其写入范围。

独立委派可用但并发缺失或不明时，回退一个写代理，继续独立验收；委派或干净验收上下文本身缺失仍按 adapter `BLOCKED`。模型选择、显示与覆写规则不因并行改变。

## 验收边界

验收前确认该范围的写代理已结束，固定当前实际改动与验证证据；验收期间该范围及相关接口、依赖不得变化。完全无关且满足并行条件的任务可继续。共享测试资源的验证按上节处理；若审查版本已变化，旧结论不能套用到新代码。

独立任务分别验收；本质不可分割的功能单元可以共用一次新 Reviewer，前提是满足依赖顺序，并为每项输出独立结论、证据和阻塞项。合并验收不允许提前派发依赖任务，也不合并或重置每项修复预算。多个任务的修复仍交各自原编码代理；每个实际修复任务计自己的轮次。

Reviewer 使用区别于全部 Coder 的干净上下文，只得到验收范围所需材料。不复制完整聊天、编码思考过程或讨论过程；不开放 Coder / Reviewer 直接交流。疑问、发现和修复反馈均经主模型转交，验收不依赖双方达成共识。

## Ledger 创建与更新

单个简单任务不创建 ledger。两个及以上开发任务，无论可并行还是有依赖必须串行，都在首次编码派发前自动创建 `.agent-tmp/dev-delegate/<task-id>/progress.md`。这里目录 `<task-id>` 是本次执行 ID，内部各项另用稳定 ID。单个长任务确需恢复记录时按需创建，不为形式建档。

输出根必须是目标项目，不能是安装缓存；遵从 [任务产物位置](../../../references/artifacts.md)。确认路径没有越出授权范围或被重定向；Git 项目用 `git check-ignore` 核对 ledger 将被忽略。未忽略时按项目授权补项目内忽略规则；无相应权限或无法建立必需记录时，派发前集中说明并停止，不静默省略。无 Git 时使用项目认可的临时位置，收尾不将其当作交付文件。

只有主模型写 ledger，子代理只返回报告或写各自指定的证据文件。记录完整当前快照，不保存聊天历史、大段 prompt、思考过程或敏感信息。最低包含：

```yaml
execution_id: 2026-10-13-1530-example
workspace: <目标项目绝对路径>
baseline: <HEAD 与原有 tracked/staged/untracked 改动证据>
max_coders: 1
final_check: PENDING
tasks:
  - task_id: A
    goal: 新增 API
    depends_on: []
    write_scope: [backend/api.py, tests/test_api.py]
    can_parallel: false
    parallel_reason: B 消费 A 的 API，顺序执行
    status: DONE
    coder: <实际编码 Agent/task id>
    reviewer: <实际独立验收 Agent/task id>
    coding_model: <实际型号；Claude 未确认时 UNKNOWN>
    coding_effort: <实际强度；Claude 未确认时 UNKNOWN>
    review_model: <实际型号；Claude 未确认时 UNKNOWN>
    review_effort: <实际强度；Claude 未确认时 UNKNOWN>
    fix_rounds: 0
    evidence: <当前改动、独立 PASS 与验证证据>
  - task_id: B
    goal: 前端接入 API
    depends_on: [A]
    write_scope: [frontend/view.vue]
    can_parallel: false
    parallel_reason: 必须等待 A 独立验收通过
    status: REVIEW
    coder: <实际编码 Agent/task id>
    reviewer: <实际独立验收 Agent/task id>
    coding_model: <实际型号；Claude 未确认时 UNKNOWN>
    coding_effort: <实际强度；Claude 未确认时 UNKNOWN>
    review_model: <实际型号；Claude 未确认时 UNKNOWN>
    review_effort: <实际强度；Claude 未确认时 UNKNOWN>
    fix_rounds: 1
    evidence: <第 1 轮修复已完成，等待本轮独立复验>
```

状态含义：`PENDING` 未派发，`CODING` 初次实现中，`REVIEW` 初验或复验中，`FIXING` 修复中，`DONE` 独立验收通过，`BLOCKED` 无法继续。补充实际阻塞列表、当前轮次阶段、任务范围的代码基线或证据路径，只记录恢复所需内容。显示过的模型策略与实际确认值分开，不能把示例 ID 或默认策略写成实际 ID。

更新时机：派发前写入任务 ID、范围和即将进入的阶段；工具返回后立即补真实 Agent/task id；编码结束、验收结束、返工、阻塞、整体检查和收尾变化后立即保存。派发前无法知道的代理 ID 标为 `PENDING_ID`，并在派发提示中注明执行 ID 与任务 ID，方便核对通知。文件不能完整保存时不继续派发新工作。

需要独立整体终审时，补记具体触发风险、当前会话型号 / 思考上限及来源、终审代理实际身份与设置、审查版本、结论和未解决问题。`final_review_escalated` 初始为 `false`，困难升级前记为 `true` 并写明依据；本次执行最多一次，不因代理重建、恢复或修复而清零。恢复先核实代理、已用升级及当前会话上限，不能重复派发仍运行的终审；代码或契约变化后只复核影响，旧结论或旧较高上限不能用于完成 `final_check`。

`fix_rounds` 记录已启动的修复轮次，初始为 `0`。启动修复前先记 `1` 或 `2` 与 `FIXING`，此时预记当前轮，只有修复加独立复验才完成该轮；修复返回改为 `REVIEW`，同轮复验不再加一。派发失败或中断保留预记轮次和阶段，先核实是否实际启动，再继续该轮，不凭猜测回退计数。第二轮复验仍阻塞则停止整个流程；通知未返回是待核实状态，不能假称失败或通过。

## 恢复与清理

1. compact、重载 Skill 或中断后，优先读取当前执行的 ledger，核对执行 ID、目标项目、需求和基线。不同执行的记录不覆盖；新任务 ID 冲突追加唯一后缀。不要因为忘记 ID 就另建一次执行重派全部任务。
2. 结合真实 Git 状态（含 staged、unstaged、新文件）、实际代码、证据和当前 Harness 代理状态核对记录。无 Git 则核对文件与已记录基线；缺失、损坏或不一致的记录保留，先恢复必要信息，不把未知状态当作未开发。
3. `DONE` 且代码及证据仍对应当前任务的，不重新开发。代码或相关契约变化则只复核影响，真实缺陷沿用剩余预算。`DONE` 不等于主模型整体检查已经完成。
4. `CODING` / `FIXING` / `REVIEW` 先确认已有代理是否仍运行、已返回或已消失。ID 未及时写回时，按执行 ID、任务 ID、原生通知或状态工具核对；无法确认是否仍在写入时停止该范围的新派发，不能新开重叠写代理。
5. 原 Coder 可恢复时优先继续；确已无法恢复才重建精简上下文，保留任务 ID、历史尝试、问题、证据与 `fix_rounds`。修复已完成但复验丢失时只补独立复验；仍在当前轮时继续当前阶段，不派发下一轮。验收代理也须独立于 Coder。
6. 中断、`BLOCKED`、必要证据不足或已授权收尾未完成时保留 ledger，汇报位置与待办。全部任务独立验收通过、主模型整体检查通过、授权收尾完成后，先汇报必要结果，再清理本次临时目录；核实绝对路径属于本次执行，不能递归清理整个 `.agent-tmp/` 或其他任务。清理方式及失败处理遵循[任务产物位置中的临时目录清理规则](../../../references/artifacts.md)。用户明确要求保留时遵从。

长期设计或验收证据确需保存时才使用 `docs/personal-dev/tasks/<task-id>/`，ledger 可引用这些证据，保持临时快照为唯一进度来源，不维护两份状态。临时文件不是持久备份；被外部清理后先恢复证据，不能假定全部任务未做或返工次数为零。
