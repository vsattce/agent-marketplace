# 任务编排与进度恢复

本文件是 [dev-delegate](../SKILL.md) 在确需并行、复杂依赖、进度恢复或高风险预检时的派发前必读契约，由主模型执行；普通任务使用主 Skill 的短路径，角色交接见 [roles.md](roles.md)。只使用文本记录和当前 Harness 原生工具，不要求调度脚本、数据库、任务图或独立工作树。

## 计划冲突预检

多任务、复杂或高风险任务在首次派发前复核已确定的 SPEC / PLAN：核对关键值、接口签名、字段含义、验收与验证要求是否一致；对共享文件、接口或上下游产出逐组核对提供 / 消费关系、依赖和写入范围。普通计划错误按 SPEC 修正并记录 Ruling，不重新设计明确业务。没有可用 SPEC / PLAN 按主入口提示准备，不沿用旧版“无计划时从任务描述直接执行”的回退。

预检结论简记在现有 ledger 或可写 PLAN；外部只读输入按准备契约使用 progress.md。未解决的关键契约冻结受影响任务，其余安全任务继续；所有角色读取同一文件版本与执行补正。复杂度和代码量本身不触发独立 Final Reviewer。

## 任务与依赖

任务从已就绪的 SPEC / PLAN 读取，不从聊天重新定义业务。每项沿用稳定 `task_id`、`goal`、`depends_on`、`write_scope`、验证与完成标准。SPEC 是最高业务约束，PLAN 局部错误由主模型按 SPEC 裁决并记录。普通少量串行任务在可写 PLAN 简记进度；确需调度或恢复才使用 ledger，不复制维护另一份计划。

- `depends_on` 使用任务 ID，检查直接和间接依赖。接口、数据结构、调用链或前项产出是后项输入时必须记录，不能因文件不同而省略。
- `write_scope` 列出相对目标项目的具体文件或目录，包含实现、测试、配置、生成文件和验证命令的写入。目录包含关系也算重叠；边界不清先串行，派发前补齐。
- `can_parallel` 只是候选资格，不是立即启动许可。默认串行；确需并行且既有 PLAN 未写标记时，主模型按下节条件判断并记录依据，不重写外部只读文件。显式 false 或用户要求串行时遵从；独立性无法确认时串行。
- 上游实际 `DONE`、独立验收通过且相关契约已确定，才解除依赖；状态简记于 PLAN 或已有 ledger。Coder 的 `DONE` 报告只进入 `REVIEW`。上游返工使已验收的契约改变时，暂停下游，复核受影响证据，不重开上游预算。
- 缺失依赖 ID、自依赖或循环先由主模型按 SPEC 修正 PLAN；无法判断时只阻塞受影响任务，不忽略依赖抢跑。简单单任务不生成任务图。

## 有限并行

默认 `max_coders: 1`，不因有多个任务或 can_parallel=true 自动并行。只有多个独立任务确有并行收益（例如可独立实现和验证、耗时足以抵消调度成本），或用户明确要求时，才启用有限并行；先记录具体理由，再结合运行中任务逐对核验以下条件。启用后通常 `max_coders: 2`，先启动本批再等待；确需第三项且槽位足够时可设 `3`，编码硬上限为三个。冲突、能力不明或用户要求串行时使用 `1`；用户指定更低上限时遵从，不因“尽快”放宽条件。

1. 本批任务之间没有直接或间接依赖，各自所需上游已经通过独立验收。
2. 修改范围明确且 `write_scope` 不重叠。
3. 不共享正在变化的接口、schema、公共配置或核心契约。
4. 当前原生工具和工作区确实支持并发子代理，主模型判断合并风险低。
5. 验证所用的输出目录、端口、fixture 或其他有副作用资源不冲突；不能隔离时将这些验证串行安排，不能确认时整项串行。

拆成不同任务的 DTO / Service / Controller / 前端调用等上下游任务、可能编辑同一文件、目录范围包含、共同修改接口或等待契约确定，均串行。不得让多个写代理在同一工作区同时修改可能重叠的文件；不为并行自动创建 worktree、多分支 merge 或 Agent Teams。

每次启动和修复前重新检查上述条件，简短展示本批并行 / 串行任务及理由；空位可补派其他安全就绪任务，不等待无关任务全部结束。编码数包含初次实现、返工和仍在运行的后台写任务；通知未到、取消未确认不能视为已释放。总活动代理数还需计入 Reviewer 和 Harness 其他代理，待验收任务及时安排 Reviewer。槽位不足先等待或减小本批，不突破三个编码上限。

单任务失败按下节隔离，不因返工次数耗尽停止无依赖安全任务。无法确认已中断的代理仍占用其槽位与写入范围。

独立委派可用但并发缺失或不明时，回退一个写代理，继续独立验收；委派或干净验收上下文本身缺失仍按 adapter `BLOCKED`。所有并行 Worker 使用同一 worker，多个 Reviewer 使用同一 reviewer；模型参数校验与显式传递规则不因并行改变。

## 任务失败隔离

仅发生真实失败、未决共享契约或具体风险传播时启用依赖冻结；普通串行任务只遵守上游先验收的顺序，不预建冻结链。按 [角色契约](roles.md#修复与收敛) 持续存在 blocker 才继续修复，最多三轮与收敛判断后仍无法解决的任务记 FAILED；缺少必要证据或能力的任务记 BLOCKED，不当作 DONE。

1. 由 depends_on 求直接和间接依赖链，依赖失败任务的后续项记 BLOCKED，记录 `blocked_by` 和证据。已运行的受影响任务用原生工具暂停 / 中断并核实状态，不让它们继续消费失败契约。
2. 其他任务只有在失败会造成具体执行风险时冻结，例如共享损坏配置、变化中的公共接口或副作用测试资源；记录风险、影响范围和解除条件。write_scope 重叠本身需串行，但不能无证据地当作全局失败。
3. 无依赖、无风险影响的任务继续，包含仍在运行的安全 Coder 与尚未派发的就绪任务。每次派发重新核对依赖、范围和槽位。
4. 仅风险覆盖所有剩余路径、平台要求停止或必需执行能力整体不可用时停止全局；说明具体依据。不能把一个 FAILED 自动传播到整图，或静默把依赖删掉绕过失败。
5. 可执行任务耗尽后仍做主模型整体检查，汇总 DONE / FAILED / BLOCKED 与风险冻结项。部分失败保留文件与 ledger，不自动提交、推送或发布混合的失败实现，不宣称整个需求完成。

## 验收边界

验收前确认该范围的写代理已结束，固定当前实际改动与验证证据；验收期间该范围及相关接口、依赖不得变化。完全无关且满足并行条件的任务可继续。共享测试资源的验证按上节处理；若审查版本已变化，旧结论不能套用到新代码。

独立任务分别验收；本质不可分割的功能单元可以共用一次新 Reviewer，前提是满足依赖顺序，并为每项输出独立结论、证据和阻塞项。合并验收不允许提前派发依赖任务，也不合并或重置每项修复预算。优先各自原 Coder，fresh coder 仅按角色契约的实际条件启用，保留同一 worker 配置；每项独立计数。

Reviewer 使用区别于全部 Coder 的干净上下文，只得到验收范围所需材料。不复制完整聊天、编码思考过程或讨论过程；不开放 Coder / Reviewer 直接交流。疑问、发现和修复反馈均经主模型转交，验收不依赖双方达成共识。

## Ledger 创建与更新

不按任务数量强制创建 ledger；普通少量串行任务默认在可写 PLAN 简记当前任务、结论与必要修复计数。仅并行调度、复杂依赖、长时 / 跨上下文恢复或只读 PLAN 确需裁决记录时，在相应派发前创建 `.personal-dev/sdd/<task-id>/progress.md`。目录 `<task-id>` 与 SPEC / PLAN 共用本次执行 ID，内部各项另用稳定 ID。旧布局恢复时复用既有 ledger，不因走短路径丢弃原状态。

输出根必须是目标项目，不能是安装缓存；遵从 [任务产物位置](../../../references/artifacts.md)。确认路径没有越出授权范围或被重定向；Git 项目用 `git check-ignore` 核对 ledger 将被忽略。未忽略时按项目授权补项目内忽略规则；无相应权限或无法建立必需记录时，派发前集中说明并停止，不静默省略。无 Git 时使用项目认可的临时位置，收尾不将其当作交付文件。

只有主模型写 ledger，子代理只返回报告或写各自指定的证据文件。记录完整当前快照，不保存聊天历史、大段 prompt、思考过程或敏感信息。最低包含：

```yaml
execution_id: 2026-10-13-1530-example
workspace: <目标项目绝对路径>
baseline: <HEAD 与原有 tracked/staged/untracked 改动证据>
max_coders: 1
spec: <SPEC 文件绝对路径>
plan: <PLAN 文件绝对路径及就绪状态>
final_check: PENDING
tasks:
  - task_id: A
    goal: 新增 API
    depends_on: []
    write_scope: [backend/api.py, tests/test_api.py]
    can_parallel: false
    parallel_reason: B 消费 A 的 API，顺序执行
    status: DONE
    coder: <实际编码 Agent/task id>
    reviewer: <实际独立验收 Agent/task id>
    worker_config: {model: <已验证实际型号>, effort: <显式强度>}
    reviewer_config: {model: <已验证实际型号>, effort: <显式强度>}
    fix_rounds: 0
    evidence: <当前改动、独立 PASS 与验证证据>
  - task_id: B
    goal: 前端接入 API
    depends_on: [A]
    write_scope: [frontend/view.vue]
    can_parallel: false
    parallel_reason: 必须等待 A 独立验收通过
    status: REVIEW
    coder: <实际编码 Agent/task id>
    reviewer: <实际独立验收 Agent/task id>
    worker_config: {model: <已验证实际型号>, effort: <显式强度>}
    reviewer_config: {model: <已验证实际型号>, effort: <显式强度>}
    fix_rounds: 1
    evidence: <第 1 轮修复已完成，等待本轮独立复验>
```

状态含义：`PENDING` 未派发，`CODING` 初次实现中，`REVIEW` 初验或复验中，`FIXING` 修复中，`DONE` 独立验收通过，`FAILED` 三轮后仍有真实核心 blocker，`BLOCKED` 依赖、风险或必要能力 / 证据阻塞。按需补 `blocked_by`、稳定 finding_id、历史尝试、convergence 裁决与影响范围，以及当前阶段、代码基线或证据路径；只记录恢复所需内容。只记录本次显式且已核验的 worker / reviewer，不把示例或历史默认值写成实际配置。旧 ledger 保留原始证据，恢复时校验本次显式配置，不用旧字段补参数。

更新时机：派发前写入任务 ID、范围和即将进入的阶段；工具返回后立即补真实 Agent/task id；编码结束、验收结束、返工、阻塞、整体检查和收尾变化后立即保存。派发前无法知道的代理 ID 标为 `PENDING_ID`，并在派发提示中注明执行 ID 与任务 ID，方便核对通知。文件不能完整保存时不继续派发新工作。

触发独立 Final Reviewer 时补记具体风险、同一 reviewer 配置、代理身份、审查版本、结论及未解决问题。恢复先核对代理、本次显式配置及累计修复预算，不重复派发，不自动升级或重置计数。

`fix_rounds` 记录已启动的修复轮次，初始为 `0`。启动修复前先记 `1`、`2` 或 `3` 与 `FIXING`，只有修复加独立复验才完成该轮；修复返回改为 `REVIEW`，同轮复验不再加一。中断保留预记轮次和阶段，先核实是否实际启动，再继续该轮，不凭猜测回退计数。第三轮复验后执行 convergence，真实核心 blocker 仍未解决则 FAILED，按依赖链隔离而非全局熔断；通知未返回是待核实状态，不能假称失败或通过。

## 恢复与清理

1. compact、重载 Skill 或中断后，优先读取当前执行的 SPEC / PLAN 与 ledger，核对执行 ID、目标项目、就绪状态和基线。不同执行的记录不覆盖；新任务 ID 冲突追加唯一后缀。不要因为忘记 ID 就另建一次执行重派全部任务。
2. 结合真实 Git 状态（含 staged、unstaged、新文件）、实际代码、证据和当前 Harness 代理状态核对记录。无 Git 则核对文件与已记录基线；缺失、损坏或不一致的记录保留，先恢复必要信息，不把未知状态当作未开发。
3. `DONE` 且代码及证据仍对应当前任务的，不重新开发。代码或相关契约变化则只复核影响，真实缺陷沿用剩余预算。`DONE` 不等于主模型整体检查已经完成。
4. `CODING` / `FIXING` / `REVIEW` 先确认已有代理是否仍运行、已返回或已消失。ID 未及时写回时，按执行 ID、任务 ID、原生通知或状态工具核对；无法确认是否仍在写入时停止该范围的新派发，不能新开重叠写代理。
5. 原 Coder 可恢复时优先继续；确已无法恢复才重建精简上下文，保留任务 ID、历史尝试、问题、证据与 `fix_rounds`。修复已完成但复验丢失时只补独立复验；仍在当前轮时继续当前阶段，不派发下一轮。验收代理也须独立于 Coder。
6. FAILED / BLOCKED 恢复时保留原轮次、finding 与冻结链，核实解除条件；不能自动重置失败任务预算。中断、失败、必要证据不足或已授权收尾未完成时保留 SPEC / PLAN 和 ledger，汇报位置与待办。全部任务独立验收通过、主模型整体检查通过、授权收尾完成后，先汇报必要结果，再仅清理本次 `.personal-dev/sdd/<task-id>/` 临时目录；需求与计划默认保留。核实绝对路径属于本次执行，不能递归清理整个隐藏根目录、文档目录或其他任务。清理方式及失败处理遵循[临时目录清理规则](../../../references/artifacts.md#临时目录清理)。prepare 确认后只交接文件，不执行开发清理。用户明确要求保留执行现场时遵从。

需求与计划默认保留在 `docs/personal-dev/specs/` 和 `docs/personal-dev/plans/`。额外验收证据确需长期保存时才使用 `docs/personal-dev/tasks/<task-id>/`，ledger 可引用这些证据，保持临时快照为唯一进度来源，不维护两份状态。临时文件不是持久备份；被外部清理后先恢复证据，不能假定全部任务未做或返工次数为零。
