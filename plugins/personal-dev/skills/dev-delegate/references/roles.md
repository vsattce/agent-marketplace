# 角色交接与验收契约

所有角色服从目标项目规则、用户授权和同一 SPEC：`SPEC > PLAN > Coder interpretation`。PLAN 冲突以 SPEC 为准；Coder / Reviewer 不重新解释已明确需求。子代理不得派生代理、自行升级配置、修改全局环境或 commit / push。只有主模型裁决计划、审查争议与调度。

## 编码代理

模型角色固定为 `worker`，包括搜索/读取文件、查引用、执行命令、修改配置、补测试、初次实现和所有修复；按[子代理模型契约](../../../references/subagent-models.md)使用本次显式配置。

交接以文件为主：目标项目、SPEC / PLAN 路径和本任务段落定位、规则路径、必要接口与基线、原有用户改动、当前阶段和验证要求。Coder 先读 SPEC，再读本任务 PLAN 及必要依赖契约，不读完整聊天或其他 Coder 讨论。有执行补正 / Ruling 时必须提供记录路径与段落并要求读取，单任务也适用；补正仍受 SPEC 约束。多任务补稳定 task_id、depends_on、write_scope、并行决定与 ledger 路径；ledger 只由主模型写。

只修改获准 write_scope，按既定验收标准实现和自检。需要扩大范围、共享测试资源冲突或上下文不足时返回主模型，由主模型按 SPEC 裁决，普通细节不转成用户问答。不得通过改写 SPEC 迁就实现。遵循项目运行时和验证深度；不为工具安装 / 切换运行时或修改 PATH。

返回 DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED，附实际文件与行为变化、验证命令和结果、未验证项与理由。报告是待核实声明，不等于验收通过。单任务简短返回；长报告 / 多轮尝试用本次目录下的文件路径交接，不反复复制全文，不用 TODO / 伪实现冒充完成。

## 独立验收代理

新建区别于全部 Coder 的干净只读上下文，提供同一 SPEC / PLAN 定位、主模型执行补正 / Ruling 的文件定位、实际改动（staged、unstaged、新文件）、编码报告与验证证据；要求先读 SPEC 和相关执行补正，不能只按未补正的外部 PLAN 验收。模型角色固定为 `reviewer`，包括 SPEC / PLAN 符合性、验证结果、回归风险与独立检查，使用本次显式 reviewer 配置。只读审查，不修复、不提交、不派生代理；需要有副作用的验证时报告主模型安排。Coder / Reviewer 不直接交流。

验收冻结当前范围及相关依赖写入，无关安全任务可继续。代码版本变化则旧证据不能证明新版本通过。一次输出：

1. **需求符合度**：PASS / FAIL / UNVERIFIED，对照 SPEC 验收项检查遗漏、误解和额外实现。
2. **质量与正确性**：PASS / FAIL / UNVERIFIED，检查实际代码、直接调用关系和必要边界。
3. **发现列表**：稳定 finding_id、对应 SPEC 条款或项目约束、文件 / 行号、触发条件、真实影响和证据；标明 blocker / 建议 / 未验证疑点。
4. **验证证据**：核对是否对应当前代码与真实行为；充分则复用，具体缺口才补针对性检查。不能只引用 Coder 的“测试通过”。

普通建议、风格偏好、可选优化单列，不作为 blocker。必要验收条件 UNVERIFIED 时由主模型补证据或将任务 BLOCKED，不能猜测 PASS。简单任务聚焦差异、验收和直接影响，不扩大到无关模块。不可分割单元可合并验收，但逐任务保留结论与预算，不能绕过依赖顺序。

## 修复与收敛

主模型先裁决 finding，再派发修复；不是所有 Reviewer 要求都交给 Coder：

| 分类 | 判定与处理 |
| --- | --- |
| 真实 blocker | 违反 SPEC 验收或适用项目 / 安全约束，或有证据的正确性缺陷使本任务不可接受；给出触发、影响与证据，进入修复 |
| 重复的同一 blocker | 按根因、触发和影响识别，即使改名也沿用 finding_id；已修复则核对当前证据，仍真实则保留，不重置预算 |
| Reviewer 新发现的问题 | 标记 NEW；核对是否属于本任务 SPEC / 必要约束或修复引入，真实 blocker 使用剩余预算，范围外观察不延长循环 |
| 非阻塞建议 | 可选覆盖、优化、可维护性建议记录即可，不阻止 PASS |
| 样式 / 偏好问题 | 没有项目强制规范或实际影响时不阻塞，不要求反复改写 |
| 超出 SPEC 的 Reviewer 要求 | 拒绝该 finding，记录 SPEC 依据；不扩大功能、不让 Coder 跟随改需求。适用安全 / 项目硬约束不能以“SPEC 未写”忽略 |

记录 `Ruling: finding_id — 接受 / 拒绝 / 非阻塞 — 证据与 SPEC 依据 — 影响`。有 ledger 时写入 ledger，否则记在可写 PLAN 对应任务下；外部只读文件的裁决按准备契约记入本次 progress.md，保持源文件原样。误判由主模型裁决，不靠双方争论或新增审查席位解决。

初次实现不计轮次；**一次修复派发 + 一次独立复验为一轮，每任务最多 3 轮**：

- **Round 1 / 2**：优先恢复原 Coder，交回全部真实 blocker、文件定位和累计轮次。原代理确实不可恢复时才重建精简上下文。
- **Round 3**：仍有真实 blocker 时，默认 fresh coder 携同一 SPEC / PLAN、当前实现、blocker、历次尝试与证据接手；始终使用同一 worker 配置，不自动更换模型或思考强度。Reviewer 仍独立于全部 Coder。
- **每轮复验**：逐项 ADDRESSED / NOT_ADDRESSED，检查修复及直接影响，不重新全项目巡查。新增真实缺陷归入同任务剩余预算，普通建议、偏好与范围外要求不延长循环。
- **第三轮之后**：主模型做一次 adjudication / convergence，按上表逐项核对当前证据，记录已解决 / 同根因未变 / 有进展 / 新问题，以及真实剩余 blocker 和裁决。只剩误判或建议时可接受；仍有无法解决的核心 blocker 则 FAILED，必要证据不可得则 BLOCKED。不能把“轮次用完”作为降级缺陷或放行的理由。**不允许第 4 轮**，包括终审、换代理、改任务名或恢复后续跑。

有 ledger 时派发修复前预记 fix_rounds=1/2/3 与 FIXING；返回记 REVIEW，复验不加一。单任务无 ledger 时在可写 PLAN 任务下简记轮次、阶段、代理 ID 与必要证据；只读 PLAN 时按需用既有 progress.md。中断先核实实际阶段，修复完成则只补复验；不重发仍运行的工作、不清零计数。具体依赖冻结和继续策略见 [编排契约](orchestration.md#任务失败隔离)。

## 整体检查与结果

触发独立 Final Reviewer 时，固定使用同一 `reviewer` 配置，另建区别于全部 Coder 与任务 Reviewer 的干净只读上下文，输入整体 SPEC / PLAN、执行补正、累计改动、任务验收与验证证据、待处理问题。冻结整体审查所涉及的范围，重点检查端到端行为、跨任务契约和触发风险，输出 PASS / FAIL / UNVERIFIED、真实 blocker、建议与证据缺口；内部实现复用有效结论，具体疑点才展开。终审 finding 沿用上面的分类和最多三轮代码修复预算，归属原任务，不新建“终审任务”绕过预算。

Reviewer 须指出具体判断困难与已检查证据，主模型先补材料；继续使用同一 reviewer 配置复核未解决问题及影响，不自动升级 effort。仍无法取得必要结论则阻塞相关任务，其他安全任务继续；代码修复仍受原任务三轮预算约束。

主模型按主 Skill 第 5 节始终检查整体 SPEC 覆盖、跨任务联动、范围、最终版本和未完成项；内部实现复用验收结论。仅规定的五类触发条件增加独立 Final Reviewer，仍用同一事实来源、finding 分类和修复预算，不按代码量或复杂度加席位。

任务 FAILED / BLOCKED 不是全局停止信号。主模型记录原因、模型 / 强度、尝试与证据、受影响依赖和可继续任务，推进其余安全工作，最终统一报告未完成项。实际执行能力整体缺失或风险覆盖全部路径时才全局停止；不擅自接手编码或宣称全部验收通过。
