# SPEC / PLAN 准备与消费契约

`dev-prepare` 与 `dev-auto` 共用本文件生成和检查需求文件；`dev-delegate` 只消费已确定的文件。流程模式由用户显式入口决定，不根据 description 自动调用入口。

## 事实来源与裁决

在平台规则、目标项目约束和用户授权内，执行 `SPEC > PLAN > Coder interpretation`。SPEC 是业务需求的最高约束；PLAN 是实现步骤，不能覆盖 SPEC。Coder / Reviewer 均读取同一 SPEC 与本任务 PLAN 段落，不自行重新解释已明确的业务需求。用户后续明确变更需求时，主模型先更新对应文件和受影响任务，再继续。

PLAN 与 SPEC 冲突时，以 SPEC 为准，主模型修正 PLAN 的受影响部分并记录 `Ruling: 决定 — SPEC 依据 — 影响`。未规定的普通实现细节按现有代码和最小合理方案裁决；没有 ledger 时记在可写 PLAN 对应任务下。有 ledger 时只在 ledger 记录执行裁决，不维护两份进度。外部只读定稿文件保持原样；确需计划补正、裁决或恢复记录时，在目标项目同一 task-id 下复用 progress.md 机制，缺失时按产物约定创建，注明原文件路径与执行补正，不复制另一套业务定义。交接须提供补正记录路径并要求 Coder / Reviewer 读取相关段落，单任务也适用。规则或授权与 SPEC 冲突时不能按 SPEC 越权。

## 生成文件（prepare / auto 共用）

1. 读取当前用户需求、目标项目实际生效的 AGENTS.md / CLAUDE.md 与直接相关约束，记录当前工作目录、Git 基线和已有改动。检查相关实现、调用点、现有测试与接口，先复用项目结构，再确定方案。只读检查代码；此阶段只写本次 SPEC / PLAN，不开发、启动写入代理或 commit / push。
2. 复用[任务产物位置](artifacts.md)：默认创建目标项目 `.agent-tmp/dev-delegate/<task-id>/spec.md` 和 `plan.md`，同一 task-id 用于后续 progress.md；不要写入 Plugin 安装目录。ID 使用用户时区日期、时间和主题，冲突追加后缀，不覆盖其他执行。需要长期留存时才用 `docs/personal-dev/tasks/<task-id>/`，或遵从用户指定位置。
3. 确认临时路径被 Git 忽略且未重定向到项目外；不能写入或缺少授权时报告具体限制，不能仅把大段正文放进聊天代替文件。两个及以上开发任务才在执行阶段建立 progress.md；单任务也必须保存 SPEC / PLAN。
4. 写简洁的 SPEC 与可执行 PLAN，再按下一节自动检查。简单需求可每节一句、PLAN 只有一个任务；不制造设计层、基础设施、长报告或重复模板。聊天只汇报文件路径、简要方案与必要风险，后续 Agent 通过文件读取，不反复粘贴全文。

SPEC 至少包含：

```markdown
# SPEC: <主题>
执行 ID：<task-id>
目标项目：<绝对路径>
## 目标
## 范围
## 明确不做什么
## 现有约束
<相关项目规则、现有接口和源码路径；必要时记录基线>
## 关键行为
## 验收标准
<可判断的行为和结果>
```

PLAN 至少包含：

```markdown
# PLAN: <主题>
执行 ID：<与 SPEC 相同>
目标项目：<绝对路径>
SPEC：<spec.md 路径>
就绪状态：DRAFT
## Task A: <名称>
- goal: <对应 SPEC 的目标 / 验收项>
- depends_on: []
- write_scope: [<相对目标项目的实现、测试或配置路径>]
- can_parallel: <true / false>
- parallel_reason: <可并行的任务与独立依据，或依赖 / 冲突原因>
- 验证方式：<按项目约束可运行的检查>
- 完成标准：<可独立验收的结果>
```

同一功能的技术层优先合为一个任务，不为凑并行拆散功能。任务 ID 唯一稳定，依赖必须存在、无自依赖或环；写入范围须包括测试、生成文件与有副作用的验证。生成 PLAN 时主动根据依赖、写入范围、共享契约与验证资源识别可并行的任务组合，填写每项 `can_parallel` 和 `parallel_reason`；独立性不明时标 false。标 true 仅代表候选资格，实际派发仍须满足[有限并行条件](../skills/dev-delegate/references/orchestration.md#有限并行)，有依赖的任务等待上游验收。记录必要接口和跨任务契约即可，不预设全部实现代码。

## 自动检查与就绪

主模型核对需求是否忠实、项目约束是否完整、关键行为和验收是否可判断；逐任务核对目标、依赖、write_scope、验证与完成标准是否足够执行，所有 SPEC 验收项是否被 PLAN 覆盖，是否有冲突、漏项、范围外工作、不可运行验证或遗漏的破坏性 / 安全边界。普通计划缺陷自行修正，不新增独立规划 Reviewer。

- **prepare 模式**：文件生成并检查后，**只进行一次人工确认**，同一次请求用户确认“SPEC 是否正确、PLAN 是否正确”，附两个路径。等待明确回复，不把沉默视为确认。用户确认后将 PLAN 就绪状态记为 `CONFIRMED`，本次调用结束，**不执行代码、不自动进入 dev-delegate**。用户要求修订则只改文件；只有回复明确接受修订结果时才记 CONFIRMED，否则保留 DRAFT 并结束，不连环确认或启动开发。
- **auto 模式**：没有重大问题时，将 PLAN 就绪状态记为 `AUTO_READY`，立即进入既有 dev-delegate 执行正文。**不确认 SPEC、PLAN、模型、effort 或是否继续，不在 Task 之间询问。**

auto 从准备到执行结束，只允许因以下三类无法自行合理裁决的情况集中询问一次：

1. **重大歧义**：不同解释会产生明显不同的最终功能，项目证据无法裁决。
2. **破坏性操作**：删除真实数据、大范围不可逆迁移、覆盖重要配置或不可逆结构调整，且当前授权未覆盖。
3. **安全边界不清**：认证、权限、密钥或安全策略存在重大未决风险。

将已知的关键问题合为一次请求，只等待所需决定；普通细节由主模型按 SPEC 与项目现状裁决。提问前在 PLAN 简记 auto 入口、询问已用和待答问题，答复后记录决定，恢复时先读取，不重置整次询问预算。答复后更新 SPEC / PLAN，继续自动检查和执行，无第二次 SPEC / PLAN 确认。一次询问后仍有重大未决项则保留文件并报告阻塞，不猜测授权、不反复询问。能力缺失、环境不满足或平台审批拒绝时如实报告限制，不伪装成功，也不把它改造成模型配置问答；平台和项目权限边界始终适用。

## 执行入口：查找与校验

`dev-delegate` 先读取用户给定的 SPEC / PLAN 路径；未给路径时，仅从本会话明确的 task-id 或当前执行 ledger 定位，不按最新时间猜选其他任务目录。用户明确指定已定稿的外部文件也可直接消费，不为格式强制重写。

核对两个文件均可读、属于当前目标项目与同一需求，PLAN 指向正确 SPEC，且内容满足上面的必要信息；自有生成文件须为 CONFIRMED 或 AUTO_READY。用户本次明确指定文件并要求按它们执行，视为对这组文件的确认，可写自有 PLAN 记录此授权；外部只读文件以用户本次指定为依据，已有 ledger 时记录路径，否则无需仅为确认建档。明确标为草稿但未授权执行的文件不可消费。

找不到可用 SPEC / PLAN 时，提示先用 `$dev-prepare` / `$personal-dev:dev-prepare`（Claude：`/personal-dev:dev-prepare`；agy：`/dev-prepare`），或 `$dev-auto` / `$personal-dev:dev-auto`（Claude：`/personal-dev:dev-auto`；agy：`/dev-auto`）；列出缺失或不一致的文件并结束。**不从自然语言重新推导业务需求，不偷偷生成另一套 SPEC / PLAN。**多个无法区分的候选也按缺少明确输入处理。

已确定的 SPEC 不因 Reviewer 偏好变化。执行前发现 PLAN 的局部错误可据 SPEC 裁决并修正；无法在既定 SPEC 内修复的核心缺口按任务阻塞处理，不能通过改写业务要求让实现或审查通过。
